# company-website

สร้างเว็บบริษัท/องค์กรจากการสัมภาษณ์ → วิเคราะห์ → แนะนำแบบที่เหมาะ → สร้างจริง. งานเชิงบริการ (ส่งมอบลูกค้าได้).

## แพลตฟอร์ม + ใครกด deploy (อ่านก่อน)

**ไฟล์นี้ self-contained — ทุกอย่างที่ต้องรู้อยู่ในนี้ ไม่ต้องเรียก skill นอก. ทำงานได้ 2 ช่องทาง:**
- **Claude Code (desktop)** — เรียกด้วย trigger / `/company-website`. ถ้าเครื่องมี skill `frontend-design` / `ui-humanize-review` → เรียกเสริมได้ (optional, ช่วยยกคุณภาพดีไซน์ — แต่ไม่มีก็ทำตาม rule ในไฟล์นี้ได้ครบ)
- **ChatGPT Codex** — ไม่มีระบบ skill/slash: ชี้ Codex มาที่ไฟล์นี้ หรือก็อปเนื้อลง `AGENTS.md`/prompt แล้วสั่ง "ทำตาม workflow นี้". ไม่ต้องเรียก skill นอก, ไม่ต้องพึ่ง path `~/.claude/...` ใดๆ

**ใครกด deploy prod:** skill สร้าง+ทดสอบ แล้วส่ง **preview URL** ให้ดูก่อนเสมอ. **เจ้าของเว็บ/ผู้ดูแลเป็นคนอนุมัติขึ้น prod** — ห้าม deploy prod เองจนกว่าจะได้ "โอเค/อนุมัติ/ขึ้นได้" ในข้อความปัจจุบัน

## เมื่อไหร่ใช้ / ไม่ใช้

**ใช้:** เว็บภาพลักษณ์, บริการ B2B/มืออาชีพ, หลายหน้า, สร้าง trust แล้วให้ลูกค้าทัก/โทร/ขอใบเสนอราคา.

**ไม่ใช้:**
- ขายตรงหน้าเดียว ยิงแอดปิดการขาย → ใช้ `/sale-page`
- ร้านค้าหลายสินค้า + ตะกร้า → e-commerce (WooCommerce/Shopify)
- ระบบมี login/database → web app

## ⭐ ผู้ใช้ = เจ้าของธุรกิจ ไม่เก่งเทค (สำคัญสุด)

client รัน skill นี้เอง. ออกแบบให้ง่ายที่สุด:
- **พูดภาษาชาวบ้าน** — ห้ามใช้ศัพท์เทคกับ user (ห้ามพูด "framework/stack/LCP/schema/Next.js/pixel"). ศัพท์พวกนี้ใช้คิดเบื้องหลังเท่านั้น. กับ user พูดเป็นภาษาคน เช่น "แบบเน้นความน่าเชื่อถือ" ไม่ใช่ "Classic Trust layout"
- **ถามทีละคำ** — ถามสั้นๆ ทีละข้อ รอตอบ แล้วค่อยถามต่อ. ห้ามยิงคำถาม 8 ข้อรวด
- **ขาดข้อมูล = ถามเลย** — ไม่ต้องให้กรอกไฟล์อะไรก่อน. ถามในแชทได้ทันที ตอบแล้วไปต่อ
- **ตัดสินใจเทคให้ user** — เรื่อง HTML/Next.js, hosting, SEO ฯลฯ skill ตัดสินเอง ห้ามถาม user
- **ให้ตัวอย่างทุกคำถาม** — user ไม่รู้จะตอบไง → ยกตัวอย่างนำ เช่น "ธุรกิจทำอะไรครับ? (เช่น รับสร้างบ้าน, คลินิกความงาม, ที่ปรึกษาบัญชี)"
- **เสนอคำตอบแนะนำทุกข้อ** *(เทคนิค grill-me)* — อย่าถามลอยๆ. ทุกคำถามแนบคำตอบที่แนะนำ ให้ user แค่ "เอาตามนี้" หรือแก้. เช่น "ปกติธุรกิจแบบคุณ CTA ที่ดีคือ 'ขอใบเสนอราคา' — เอาแบบนี้ไหม?" ลด load การคิดของ user
- **ไล่ทีละกิ่ง แก้ dependency ก่อน** *(grill-me)* — คำตอบข้อก่อนกำหนดข้อถัดไป (เช่น รู้ว่าเป็นคลินิก → คำถาม trust จะเจาะใบอนุญาต/หมอ). ไม่ถามสุ่ม
- **สรุปให้ยืนยันก่อนทำ** — เอาที่เก็บมาสรุปสั้นๆ ให้ user พยักหน้า ป้องกันเข้าใจผิด

## หลักการเว็บ (เบื้องหลัง — ไม่พูดกับ user)

เว็บบริษัท = **น่าเชื่อถือ → คนเชื่อ → ทัก/โทร**. ไม่ใช่ขายตรง. ทุก decision วัดด้วย "เพิ่มความเชื่อ + ดัน lead ไหม".

7 best practices ที่ต้องผ่านทุกเว็บ:
1. **Above-the-fold ชัดใน 5 วิ** — บริษัททำอะไร + ให้ใคร + CTA. คนไม่ scroll หาเอง
2. **Trust signals** — โลโก้ลูกค้า, รีวิว, ตัวเลข (ปี/จำนวนงาน), ใบรับรอง, ทีมหน้าจริง
3. **1 CTA หลักทั้งเว็บ** — เช่น "ปรึกษาฟรี"/"ขอใบเสนอราคา". ปุ่มมุมบนขวา + ซ้ำท้ายทุก section
4. **Speed** — LCP < 2.5s. รูป WebP, lazy load. ช้า = เด้งออก
5. **Responsive = พื้นฐานบังคับ (ห้ามข้าม)** — 70%+ มาจากมือถือ. ทุกเว็บต้อง: `<meta name="viewport" content="width=device-width, initial-scale=1">` · ออกแบบมือถือก่อนแล้วขยาย · breakpoint มือถือ+แท็บเล็ต · ปุ่ม/ลิงก์แตะง่าย (≥44px) · ไม่มี scroll แนวนอน · รูป `max-width:100%`
6. **SEO ฐาน** — title/meta, H1 เดียว/หน้า, schema Organization, sitemap
7. **Light mode เสมอ** — พื้นหลังสว่าง (ห้าม dark bg เว้นแบรนด์กำหนดชัด)

## Phase 0 — สัมภาษณ์ (default: ถามในแชท)

**ทักทายสั้นๆ แล้วเริ่มถามทีละคำ** ในภาษาชาวบ้าน + ยกตัวอย่างนำทุกข้อ. ไม่ต้องให้ user กรอกไฟล์.

ลำดับถาม (ทีละข้อ รอตอบก่อนถามต่อ):
1. "ธุรกิจทำอะไรครับ?" *(เช่น รับสร้างบ้าน / คลินิกความงาม / ที่ปรึกษาบัญชี)*
2. "ลูกค้าคือใคร?" *(เช่น เจ้าของบ้านงบ 3-5 ล้าน / ผู้หญิง 30+ อยากดูดี)*
3. "อยากให้คนเข้าเว็บแล้วทำอะไร?" *(โทรหา / ทัก LINE / กรอกฟอร์มขอราคา)* → เก็บ **ปลายทาง** ด้วย (เบอร์/LINE ID)
4. "บริการหลักมีอะไรบ้าง?" *(list 3-6 อย่าง)*
5. "มีอะไรให้ลูกค้าเชื่อใจบ้าง?" *(รีวิว / ผลงานเก่า / ปีที่ทำมา / ลูกค้าดังๆ / ทีมงาน)*
6. "มีโลโก้/สีแบรนด์/รูปไหมครับ?" *(ส่งไฟล์มาได้เลย ไม่มีก็จัดให้)*
7. "มีชื่อเว็บ (domain) ที่จะใช้ไหม?" *(ไม่มีก็ได้ ทำตัวอย่างให้ก่อน)*

**กติกา:**
- ข้อไหน user ตอบ "ไม่มี/ไม่รู้" → ไม่บล็อก. จดว่าขาด แล้วไปต่อ (เติมทีหลัง/skill เสนอให้)
- ถ้ามีคนชอบกรอกเอง → ยื่นหัวข้อ 7 ข้อข้างบนให้กรอกในแชท (หรือใน Claude Code: ก็อป `company-brief.template.md` ในโฟลเดอร์ skill ไปกรอก). ทางเลือก ไม่ใช่บังคับ
- **ห้ามเดา** ข้อมูลธุรกิจ. ไม่ชัด → ถามซ้ำแบบง่ายลง
- ถามครบ → **สรุป 4-5 บรรทัดให้ user ยืนยัน** ("สรุปนะครับ: ...ถูกไหม?") ก่อนไป Phase 1

## Phase 1 — วิเคราะห์ + เสนอ Layout

วิเคราะห์ประเภทธุรกิจเบื้องหลัง → แมปเป็น layout → **เสนอ user ด้วยภาษาชาวบ้าน** (ห้ามพูดชื่อ layout ภาษาอังกฤษ). แนะนำอันเด่น 1 อัน + เหตุผลสั้น, บอกทางเลือกอื่นสั้นๆ.

**ตารางแมป (เบื้องหลัง — ไม่โชว์ user):**

| Layout (ภายใน) | พูดกับ user ว่า | เหมาะกับ | Section flow |
|--------|------|----------|--------------|
| **A) Classic Trust** *(default)* | "แบบเน้นน่าเชื่อถือ ดูมืออาชีพ" | บริการ, รับเหมา, ที่ปรึกษา, คลินิก | Hero(headline+CTA) → โลโก้ลูกค้า → บริการ 3-4 การ์ด → Why us → เคส/รีวิว → ทีม → CTA+ฟอร์ม → Footer |
| **B) Story-Driven** | "แบบเน้นเล่าเรื่องแบรนด์ ดูพรีเมียม" | luxury, craft, งานดีไซน์ | Hero full-image → ปัญหาลูกค้า → วิธีเรา(story) → ผลลัพธ์/ตัวเลข → รีวิว → CTA |
| **C) Product-Led** | "แบบเน้นโชว์ตัวสินค้า/แอป" | SaaS, tech, มีของโชว์ | Hero+screenshot → ฟีเจอร์เด่น(สลับซ้าย-ขวา) → ราคา → FAQ → CTA |

**เกณฑ์เลือก (เบื้องหลัง):** บริการ/รับเหมา/คลินิก/ที่ปรึกษา→A · premium/มีสตอรี่/งานสวย→B · มี software/แอปโชว์→C

**พูดกับ user แบบนี้:** "จากที่เล่ามา ผมแนะนำเว็บ**แบบเน้นน่าเชื่อถือ** เพราะธุรกิจ[...]ลูกค้าต้องมั่นใจก่อนตัดสินใจ — หน้าเว็บจะมี[ยกตัวอย่าง section เป็นคำคน]. เอาแบบนี้ไหมครับ? หรืออยากได้แนวเล่าเรื่องแบรนด์มากกว่า?"

**รอ user เคาะ** ก่อนไป Phase 2.

## Phase 2 — Content Plan

หลังเคาะ layout:
1. **Sitemap** — หน้าไหนบ้าง (Home / About / Services / Cases / Contact — ปรับตามธุรกิจ). เว็บเล็ก = single-page anchor sections ก็ได้
2. **Copy ต่อ section** — headline, body, CTA. ดึงจาก brief. เขียนโทนตาม CI แบรนด์
3. **วาง trust signals** — ระบุว่าอะไรไปตรงไหน (โลโก้ลูกค้าใต้ hero, รีวิวก่อน CTA ท้าย)
4. **CTA เดียว** — ยืนยัน action หลัก + ปลายทาง (ฟอร์ม/LINE/โทร)

Output = content-plan สั้นๆ ต่อ section. เขียนใน `./content-plan.md`.

## Phase 3 — Wireframe (สัญญาก่อน build)

ทำ `wireframe.html` = โครงเทา กล่อง+ป้ายกำกับ ทุก section ตาม content-plan. เป็น "สัญญา" ให้ build ตรง 100% (port ไม่ใช่เดา).

กติกา wireframe:
- กล่องเทา + ข้อความจริงจาก content-plan (ไม่ใช่ lorem)
- ระบุ: ลำดับ section, ตำแหน่ง CTA, จุด trust signals, breakpoint มือถือ
- **ให้เจ้าของเว็บดู + ยืนยัน** ก่อน build. ไม่ยืนยัน = ไม่ build

## Design DNA — ห้ามให้ดูเหมือน AI ทำ (ใช้ตอน Phase 3-4)

**กฎด้านล่างนี้คือแหล่งจริง (ทำตามได้ครบในทุกแพลตฟอร์ม).** ถ้าอยู่ Claude Code และมี skill `frontend-design` (Anthropic) → เรียกเสริมได้ (optional). ถ้าอยู่ Codex/ไม่มี skill → ทำตามกฎนี้ตรงๆ พอ:
- **เลือกทิศทางดีไซน์ชัด 1 อย่าง** ตามธุรกิจ (มินิมอลหรู / editorial / อบอุ่นออร์แกนิก / industrial) แล้วทำให้สุด — อย่ากลางๆ
- **ฟอนต์เด่น** — ห้าม Inter/Roboto/Arial/system default. Thai UI: ใช้ฟอนต์ไทยมีคาแรกเตอร์ (Anuphan / IBM Plex Sans Thai / Noto Serif Thai) คู่กับ display face. ตั้ง letter-spacing/line-height เอง
- **ห้าม purple gradient บนพื้นขาว** (ลายเซ็น AI อันดับ 1). ใช้ accent สีเดียวเด็ดขาดจากแบรนด์
- **hierarchy จริง** — display 48-72px คู่ body 15-16px. ไม่ใช่ไล่ทีละนิด
- **asymmetry** — ซ้าย-align, off-center, grid-break. ไม่เซ็นเตอร์ทุกอย่าง
- **neutrals มี tint** (เทาอมอุ่น/เย็น) ไม่ใช่ #666 ล้วน · **radius** commit อันเดียว · **bg มี texture** (grain/noise/off-white) ไม่แบนเปล่า
- **ห้าม emoji ในดีไซน์** — ใช้ **icon SVG** แทน (ดู Assets)

### ตัดสินใจดีไซน์ให้ user เอง — ห้ามถามปลายเปิด (สำคัญ)
non-tech ตอบไม่ได้ว่า "อยากได้ฟอนต์ไหน/สีอะไร". **skill เลือกให้เลย** จากประเภทธุรกิจ+แบรนด์ แล้วค่อยให้ดู. ห้ามถาม "ชอบแบบไหน" ลอยๆ.
- **ฟอนต์ default (ไทย) — เลือกให้ตามโทน ไม่ต้องถาม:**
  - หัวข้อ: **Kanit** (หนา มั่นใจ ทั่วไป) · **Prompt** (โมเดิร์นเรียบ) · **Anuphan** (พรีเมียมนุ่ม) · **Bai Jamjuree** (เทค/สตาร์ทอัพ)
  - เนื้อหา: **Sarabun** (default อ่านง่าย) · **IBM Plex Sans Thai** (เทค) · **Noto Sans Thai**
  - จับคู่ให้ต่าง weight/character ชัด (หัวข้อหนา + เนื้อปกติ)
- สี: ดึงจากโลโก้/แบรนด์ก่อน; ไม่มี → เลือก accent เดียวเข้าธุรกิจ (ห้าม purple gradient)

### เสนอ 2 ทิศทางให้เลือก "ด้วยตา" (แทนถามศัพท์)
ก่อน build เต็ม — ทำ **ตัวอย่างสไตล์ 2 แบบ** (hero + สี + ฟอนต์ + โทน ต่างกันจริง) ให้ user **ดูภาพแล้วชี้เลือก 1**. non-tech เลือกจากที่เห็นได้ ไม่ต้องรู้ศัพท์. เลือกแล้วค่อย build เต็มตามแบบนั้น.

### Environment ปลายทาง → ผลต่อฟอนต์ (กันพลาดที่เจอจริง)
- **default: ไฟล์เปิดเบราว์เซอร์ / deploy Vercel** → โหลด Google Fonts ผ่าน `<link>` ได้ปกติ (+ `<meta viewport>` + `<meta charset>` เสมอ)
- **ถ้า output ไปอยู่ sandbox/preview ที่ CSP บล็อก CDN** (เช่น Artifact) → `<link>` ฟอนต์โดนบล็อก = fallback เงียบ → ต้อง self-host/embed ฟอนต์ หรือยอมรับ system fallback. **บอก user ให้ชัดว่าฟอนต์จริงเห็นตอนไหน**

## รูปภาพ & ไอคอน (ใช้ตอน build)

**รูปภาพ — เรียงตามลำดับ:**
1. **รูปจริงของลูกค้าก่อนเสมอ** (ที่ user ส่งมาใน Phase 0) — ของจริง > stock
2. ไม่มี → ดึงจากแหล่งฟรีเชิงพาณิชย์ (ไม่ต้อง attribution): **Unsplash, Pexels, Pixabay**
3. (Claude Code เท่านั้น, optional) จัดการ asset ละเอียด/AI-gen → skill `media-use`
4. **ห้าม:** โหลดรูปมีลิขสิทธิ์, รูปแบรนด์/คู่แข่ง, รูปคนที่อ้างเป็นลูกค้าจริงทั้งที่ไม่ใช่ (โกหก trust)

**ไอคอน — ใช้ SVG set ห้าม emoji:**
- default **Lucide** (lucide.dev) — inline SVG, สะอาด, ปรับสี/ขนาดได้. หรือ Heroicons
- คุมสไตล์ให้ชุดเดียว (stroke width เดียว) ทั้งเว็บ

## Phase 4 — Build

**skill เลือก stack เอง — ห้ามถาม user** (เป็นเรื่องเทค). กติกาตัดสิน:

| เงื่อนไขจาก brief | เลือก | Deploy |
|-------|-------|--------|
| เว็บนิ่ง เนื้อหาไม่เปลี่ยนบ่อย ไม่ต่อ backend *(ส่วนใหญ่)* → **default** | HTML static | Vercel static |
| หลายหน้าจริง / ฟอร์มต่อระบบหลังบ้าน / จะต่อยอดเป็นระบบ | Next.js + Tailwind | Vercel |

ค่า default = HTML static (เบา เร็ว ส่งลูกค้าง่าย). ขยับไป Next.js เฉพาะเมื่อ brief บอกชัดว่าต้องมีระบบ.

Build โดย **port 1:1 จาก wireframe**. บังคับ:
- **responsive (พื้นฐาน — ทุกไฟล์):** ใส่ `<meta viewport>` เสมอ, mobile-first (เขียนมือถือก่อน ขยายเป็น desktop), มี breakpoint มือถือ+แท็บเล็ต, ปุ่มแตะ ≥44px, รูป max-width:100%, ไม่มี scroll แนวนอน
- 1 CTA ซ้ำทุก section
- รูป WebP + lazy load
- light mode
- semantic HTML (header/nav/main/section/footer), H1 เดียว/หน้า
- **CTA = ปุ่มช่องทางติดต่อตรง (default — required, ห้าม placeholder ตาย):** ใช้ **ปุ่มคลิกไป LINE / Messenger / Facebook / TikTok / YouTube / โทร** ตามที่ธุรกิจมี. ช่องทางพวกนี้ **แจ้งเตือนเจ้าของเองในแอป** — เจ้าของเห็นทันทีที่มีคนทัก
  - ✅ **หลีกเลี่ยงฟอร์มกรอก** — ฟอร์มเก็บข้อมูลเฉยๆ **ไม่แจ้งเตือน** เจ้าของไม่รู้ว่ามีคนติดต่อ (เว้นแต่ต่อระบบแจ้งเตือนจริง)
  - ใส่ลิงก์จริง: `https://line.me/R/ti/p/@id` · `https://m.me/page` · `tel:` · ลิงก์ FB/TikTok/YouTube ของธุรกิจ
  - **test กดทุกปุ่ม 1 ครั้ง** ว่าเปิดถูกแอป/ถูกเพจก่อนบอกเสร็จ
  - ถ้าจำเป็นต้องเก็บข้อมูลลง database จริง (สมาชิก ฯลฯ) → `/backend-connect` แยกต่างหาก

## Phase 5 — QA Checklist (gate ก่อนส่ง)

**บังคับรันจริง — ห้ามข้าม:** ต้อง**เปิดเว็บดูจริง**แล้ว**ติ๊กครบทุกข้อด้วยตา**ก่อนพูดคำว่า "เสร็จ". ข้อไหนไม่ผ่าน = **ยังไม่เสร็จ** กลับไปแก้. (บทเรียนจริง: `<meta viewport>` เคยหลุดเพราะเขียน gate ไว้เฉยๆ แต่ไม่รันจริง — อย่าให้ซ้ำ)

```
□ above-fold: บริษัททำอะไร+ให้ใคร+CTA ชัดใน 5 วิ
□ trust signals ครบ (โลโก้/รีวิว/ตัวเลข/ทีม อย่างน้อย 2)
□ 1 CTA หลัก ซ้ำทุก section
□ **CTA = ปุ่มช่องทาง (LINE/Messenger/FB/TikTok/YouTube/โทร) — กดทุกปุ่มเปิดถูกที่จริง** (ห้าม placeholder ตาย, เลี่ยงฟอร์มที่ไม่แจ้งเตือน)
□ responsive: มี `<meta viewport>` · เทสจริงที่ ~390px (มือถือ) + แท็บเล็ต · layout ไม่แตก · ปุ่มแตะ ≥44px · ไม่มี scroll แนวนอน
□ speed: รูป WebP+lazy, LCP < 2.5s (เช็ค Lighthouse ถ้าทำได้)
□ SEO: <title>+meta description, H1 เดียว, schema Organization (JSON-LD), sitemap.xml
□ light mode, ตรง CI แบรนด์ (สี/ฟอนต์/โลโก้)
□ ตรง wireframe ทุก section (เทียบทีละจุด)
□ ไม่เหมือน AI ทำ: เทียบกับ Design DNA — ฟอนต์เด่น(ไม่ใช่ system), ไม่มี purple gradient, hierarchy ชัด, asymmetry, ไม่ใช่ radius 8px ทุกอัน, bg ไม่แบนเปล่า
□ ใช้ icon SVG (Lucide) ไม่ใช่ emoji
□ รูปจากลูกค้า/แหล่งฟรี (license ชัด) ไม่มีรูปลิขสิทธิ์
```

verify จริง: **เปิดเว็บดูจริง** (เปิด browser/preview, ดูทั้ง desktop + มือถือ ~390px) — ไม่ใช่แค่เชื่อว่าโค้ดถูก.
- **Claude Code:** เรียก `ui-humanize-review` กับหน้าที่เสร็จได้ (optional) — ถ้าคะแนน AI-slop สูง (>8) แก้ row ที่ได้ score 2 ก่อน
- **Codex/ไม่มี skill:** ไล่ checklist "ไม่เหมือน AI ทำ" ด้านบนด้วยตาเอง แก้ที่หนักสุดก่อน

## Phase 6 — Deploy

- **จบที่ preview ก่อนเสมอ → เจ้าของเว็บ/ผู้ดูแลอนุมัติ → ค่อยขึ้น prod** (non-negotiable): build→test→**ส่ง preview URL**→รอ "โอเค/อนุมัติ"→deploy prod. ห้ามข้ามขั้นขึ้น prod เอง
- HTML → static host / Vercel. Next.js → `vercel` (ได้ preview URL) แล้ว `vercel --prod` (หลังอนุมัติ)
- หลัง live: ยิง sitemap เข้า Search Console, เช็คมือถือจริง
- *(หมายเหตุ: ถ้ารันในเครื่องของ Mark ให้ยึด deploy policy ของ Mark — ขออนุมัติ Mark. ถ้า client รันให้เว็บตัวเอง = client คืออนุมัติ)*

## Phase 7 — Optimize Speed (หลัง live)

**เน้นเฉพาะความเร็ว.** (SEO ทำเป็น skill แยก — ดูท้ายไฟล์ "ต่อยอด"). วัดด้วย Lighthouse / PageSpeed Insights, รายงานผลภาษาชาวบ้านให้ user.

```
□ Performance ≥ 90, LCP < 2.5s, CLS < 0.1, INP ต่ำ
□ รูป: WebP/AVIF + ระบุ width/height (กัน layout ขยับ) + lazy load ใต้ fold + ขนาดพอดี (ไม่ยัดรูป 4000px)
□ ฟอนต์: preload + font-display:swap + subset ไทย (ตัด glyph ไม่ใช้)
□ CSS/JS: minify, ตัด dead code, inline critical CSS ส่วน above-fold, defer script
□ cache headers + CDN (Vercel มีให้อัตโนมัติ)
□ ลด request: รวม icon เป็น SVG sprite, ไม่โหลด lib เกินจำเป็น
```

เป้า: เปิดเว็บติดใน < 2.5 วิ บนมือถือ 4G. ช้า = คนหนี + Google ลดอันดับ. แก้จนเขียว แล้วสรุปผลให้ user ("ตอนนี้เว็บเปิดไวขึ้น X → ลูกค้าไม่หนี").
